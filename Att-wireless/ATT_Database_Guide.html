AT&T Backend Architecture & Database Guide

A support-ticket reference and onboarding guide for the AT&T Wireless client application: how the backend is put together (servers, services, AT&T integrations and key flows) and its databases, covering both the shared g3-core platform and the AT&T-specific att-cp overlay.

This guide exists so that anyone — a support engineer chasing down a customer complaint, or a new team member trying to understand how the AT&T portal is put together — can find, in one place, what database engine is used, what the tables mean, how a customer action turns into database reads and writes, and what SQL to run to investigate a specific problem. It was built by reading the actual source code of both repositories (g3-core and att-cp), not by guessing. Every table, column, and flow described here cites the file it came from; anything the source code didn't confirm directly is explicitly marked inferred, and anything that couldn't be found at all is stated as "Not found in code" rather than guessed at.

This guide serves two audiences at once. As a support reference, jump straight to the troubleshooting query cookbook (section 7 of the architecture page), for ready-to-run, read-only SQL covering the most common investigations (finding a customer, tracing a failed payment, checking why an invoice looks wrong, and more). As an onboarding document, start with Section 2 for the plain-English backend architecture story, then work through the schema and activity sections to build a mental model of how the system fits together.

2. Backend architecture

Start with the big picture. The backend does two kinds of work. Some happens live, while a user waits for a page. The rest happens in the background, keeping local copies of AT&T data up to date. The detailed diagram further down fills in the individual services.

2a. The big picture

What's happening, step by step

  1. A user opens the portal. An AT&T business customer (Premier or FirstNet) or an AT&T CSR opens the Bill Analyst portal, either directly or from a link in the AT&T business dashboard. Before anything else, the front door sends them to AT&T to sign in. We never see AT&T passwords; AT&T tells us who the user is.
  2. The page asks for data. Every screen (bill summary, invoices, usage, payments) is a page that asks the business logic layer for what it needs. Older screens use the classic page engine (COM / CV13, the older Windows components behind the ASP pages) and newer React screens use the GAS APIs, but both do the same job.
  3. Some answers need AT&T right now. A few things can't come from a copy because they must be live: taking a payment (AT&T CSI), fetching a bill PDF or switching paperless (Telegence, through the TLGEJB bridge), sign-in and user profiles (AT&T identity, Premier / PAM), and sending emails (CBUS). If AT&T is slow or down, the user sees it straight away.
  4. Everything else comes from our databases. Most of what a user sees (accounts, bills, reports, users, permissions, labels) is read from Globys's own SQL Server databases, which is why most screens are fast. Changes the user makes are saved there too.
  5. AT&T keeps sending us data. In the background, independent of any user, AT&T streams changes to us: Kafka events, message queues, a live copy of the Telegence database (accounts and unbilled usage, through GoldenGate), and file drops. The files are BEST for billed data, plus unbilled usage files from Telegence and Enabler.
  6. Background workers keep the copies fresh. Small Globys services read those feeds and write them into the databases. SQL Agent jobs then move the data into the tables the portal reads, so by the time a user opens a page the data is already local.

The rule of thumb for support: an error or timeout on a page usually means the live path (steps 1–4): the portal, GAS, or an AT&T system it calls. Old, missing or wrong data with no error usually means the background path (steps 5–6): a feed or worker has stopped, or a sync job hasn't run yet.

What's happening in each area

Each card matches a lettered area of the diagram and uses the same box names, in the same order. The grey text after a name is the real system name, which matches the small grey text in the diagram.

AWhere users come from

  • AT&T customers & support agents: AT&T business users (Premier, FirstNet) and AT&T CSRs open the portal in a browser. They go straight to the customer portal.
  • AT&T business dashboard Convergence BDC Dashboard · business.att.com/manage: a dashboard for AT&T business customers, which links them into our portal without a second login. There are two kinds of link:
    • Page links (statements, one statement, payment, paperless, autopay) go straight to the customer portal through a bridge page. The dashboard and portal share the same sign-in, so the user is already signed in. Paperless and autopay can even be shown inside the dashboard.
    • Report downloads go through the link router, which checks a signed pass from the dashboard.
    When a user arrives from the dashboard, the portal shows a "Back to Dashboard" link.

Nothing runs here. This is just where traffic starts.

BFront door

  • Link router Redirector: checks that a dashboard link is genuine, then forwards the user to the right page in the portal.
  • Customer portal (web pages) Bill Analyst: the screens users see. Older classic screens get their data from the classic page engine, and newer screens get theirs from the main API. It carries AT&T and FirstNet branding plus a few AT&T-only pages (logout, bill PDF, remittance PDF).
  • Sign-in service GAS AuthSite: when a user needs to sign in, it sends them to AT&T sign-in to check the login. It then asks the main API to set up the user's session.

When it breaks: users can't reach the portal, get stuck in a login loop, or a dashboard link lands on the wrong page.

CBusiness logic

  • Classic page engine COM / CV13: the older code behind classic screens. For each action it runs one saved database query and returns the result. It covers bills, account hierarchy, reports and payments. When a user opens a bill it asks the bill document service to get the bill PDF.
  • Main API (business services) GAS Services: the modern engine behind newer screens: payments, user setup, reports, organisations, invoices and disputes. It includes AT&T add-ons for installment plans and data pooling. It takes payments through AT&T payments, looks up users in AT&T user profiles, and asks the billing bridge for bills.
  • Bill document service GCS + BDF: creates and serves bill PDFs. PDF orders wait in a queue that is checked every minute, and finished files go to PDF & file handling.
  • Usage bridge EnablerEJB and Billing bridge TLGEJB: translators. AT&T's billing and usage systems only accept a special kind of Java call, so these two services turn our normal requests into those calls. The billing bridge reads bills and changes paperless settings in the AT&T billing system. The usage bridge can read usage details from the AT&T usage system, but nothing in att-cp calls it, and Enabler isn't in the runbook's list of AT&T APIs. Enabler usage reaches us as files instead, so the usage bridge is probably unused.
  • Paperless sync PBS service: when a customer turns paperless billing on or off, it passes the change to the billing bridge.
  • Email sender Notification service: builds emails and sends them through the AT&T email service.
  • The thick line on the left shows that the classic page engine and the main API both read and write the databases.

When it breaks: one feature fails with an error. For example, a payment fails, a bill PDF won't open, a paperless change doesn't stick, or an email never arrives.

DBackground workers

These run all the time, whether or not anyone is using the portal. Each one takes something AT&T sends (the blue boxes at the top of this area) and saves it into a database.

  • PDF & file handling PDF Cataloger · Large-BAN PDF: takes the PDF files from the bill document service, records each one in the main portal databases, and moves files to where they belong. It also handles PDFs for very large accounts.
  • File loader SSIS pipelines: when AT&T's file drops arrive, it loads them. The files go to different places:
    • BEST: AT&T's billed data (bills and statements). It goes into the loading area and then the main portal databases.
    • Unbilled usage files: Enabler (unbilled usage summary and detail) and Telegence (unbilled usage). Pipelines enabler, enabler_unbilled_detail, telegence_unbilled and mms load them into AT&T data copies.
    • CARE: the device inventory feed, one of the inventory report's inputs (batch type "Care", ATT-2837).
  • Billing DB mirror Oracle GoldenGate: every change in the AT&T billing system (Telegence) database is copied into AT&T data copies. It carries billing account and reference data (customers, billing accounts, subscribers, addresses, devices, service agreements and features), payment transactions, installment plans (INST_INFO), bill cycle control, and unbilled usage (the usage and pnbi* copies). SQL Agent jobs then turn this into payments, autopay status, paperless status and inventory report data. It does not carry billed statements; those come from BEST.
  • Account & label feeds HYFE · Platform Handler: read AT&T's Solace message queues and save them into AT&T data copies. HYFE carries foundation accounts (FANs) and organisations, including custom field labels (UDL). Platform Handler carries which bill presentation system (handler) each foundation and billing account uses.
  • Event readers CCS · IRS · CPC · ASLA: read AT&T's Kafka event streams. CCS carries unbilled data and messaging usage detail, saved into unbilled usage. IRS/DLC (user and basic handset data) and CPC (handset IMEI and feature names) feed the device inventory report in AT&T data copies. ASLA works the other way: it sends our user and CSR login/logout events to AT&T's security log audit, which is why that arrow points both ways.

When it breaks: there's no error, but data goes stale or missing. For example, yesterday's bill isn't there, a new label doesn't show, the device list is old, or unbilled usage stops changing.

EDatabases

  • Main portal databases att_config_prod_db · att_custom_db · cv_system_db: what the portal reads. They hold accounts, users, bills, permissions, AT&T-only tables, the bill document list and emails.
  • Loading area att_integrations · att_load_db: BEST billed files are unpacked and checked here first, then loaded in to the main portal databases.
  • AT&T data copies golden_gate: Telegence account data and unbilled usage (from the billing DB mirror), unbilled usage files from Telegence and Enabler, and everything the feed readers save. Scheduled database jobs copy it on to the loading area and to unbilled usage, and to the main portal databases (not drawn).
  • Unbilled usage att_unbilled_usage: usage that isn't on a bill yet. It's copied on from AT&T data copies, plus 5G usage saved directly by the event readers.

When it breaks: everything slows down or fails at once. If only some data is wrong, the cause is usually a background worker (area D) or a copy job, not the database itself.

FAT&T systems

These are owned and run by AT&T, not Globys. Top to bottom, as in the diagram:

  • AT&T sign-in: confirms who the user is (Premier / FirstNet login).
  • AT&T payments + T&C consent CSI · SmartPay · ExpressPay: CSI (7 calls) takes one-time payments (bills and installment-plan payoff) and manages autopay enrolment. SmartPay (2 calls) handles payment terms and conditions. ExpressPay is AT&T's payment page, embedded in ours, where users add a card or bank account. Autopay payments themselves are processed by AT&T outside our application.
  • AT&T user profiles & permissions Premier profile · PAM: who the user is and which accounts they can see.
  • AT&T email service CBUS: delivers emails for us.
  • AT&T billing system Telegence: sends us account data and unbilled usage in the background, and serves bill images (PDFs) and paperless settings live through the billing bridge.
  • AT&T usage system Enabler: unbilled usage (summary and detail), sent to us as files.
  • AT&T upgrade eligibility MRE API: device upgrade eligibility for the inventory report. It isn't drawn. The inventory report pipeline calls it through the "MRE Updater" jobs.

When it breaks: we can't fix it ourselves. Confirm our side is healthy (the service's health check and logs), then raise it with AT&T through the escalation path in this customer's runbook.

GGlobys cloud

  • Globys cloud data platform Forge · Azure: Globys's newer platform. It is becoming the main home for bills, usage (call records) and payments. It connects to the portal in four ways:
    • It receives a copy of every change in the main portal databases (accounts, users, payments, disputes, permissions and more), using SQL Server change capture. This is the long arrow along the bottom.
    • Usage data is exported to it as files. After export, the usage rows can be deleted from our SQL databases.
    • It runs the back end of the AT&T business dashboard, including the signing keys the link router checks.
    • It sets up users by calling our main API (not drawn).

Watch out: it doesn't copy anything back to our databases. If data is missing from SQL but the customer can see it, it may now live only in the cloud platform, or it was exported and deleted from SQL.

3. Key flows

The same diagram, traced for the requests and jobs that most tickets involve.

Sign-in

  1. The user arrives from Premier / FirstNet, or from the AT&T business dashboard. Dashboard page links reuse the shared sign-in. Report-download links go to /redirector, which checks the signed token against keys held on the Globys cloud data platform (Forge).
  2. GAS AuthSite completes SAML, OAuth/OIDC or CAS cookie exchange with AT&T identity.
  3. UserProvisioning calls the Premier profile service (HALO client certificate) or PAM. It then writes the user, accounts and permissions into att_config_prod_db.
  4. The browser lands on the Bill Analyst portal. Login and logout events go to att_custom_db, and the ASLA publisher sends them on to AT&T Kafka.

Viewing a bill

  1. The ASP statement page calls the classic page engine (COM), which looks up the document endpoint in t_bill_doc_type_config.
  2. The classic page engine calls the BDF Globys.Att.Documents WCF service, which runs inside GCS.
  3. Bill lists and bill images for Telegence accounts come through TLGEJB (/statement/pdf) into Telegence EJBs.
  4. Report and PDF orders are queued in ROQS. BdfOrderProcessor (every minute) writes them to the ROP share and the PDF pickup folder, and PDF Cataloger catalogs them into cv_system_db.

Making a payment / autopay

  1. The React payment UI calls GAS Payments (ServiceMcp).
  2. Card and bank details are captured in AT&T's ExpressPay page, embedded in ours, and tokenized (/payments/v1/tokenize/init/attcc | atteft).
  3. The ATT_Common CsiApiService calls AT&T CSI over SOAP: AddPayment, ManageAutomaticPayments, InquirePayments and so on.
  4. SmartPay T&C consent is recorded through the corpops TermsAndAgreement API. Payment state is in the payment DBs and golden_gate autopay caches.

Paperless billing

  1. The paperless / bill-format change is made in the portal and saved in att_config_prod_db.
  2. The PBS service calls TLGEJB /bill/addressInfo/{acct} (GET / PUT / DELETE).
  3. TLGEJB updates the bill format in Telegence over t3 EJB.
  4. The golden_gate job "Run GG Paperless Billing Integration" keeps the paperless_bill_state cache in step.

Real-time feeds (continuous)

  1. GoldenGate replicates Telegence Oracle schemas (BAN, reference data, unbilled usage) into golden_gate.
  2. HYFE reads FAN/UDL, PDP and authorized-email-domain messages from the AT&T broker. Platform Handler reads platform events from the same broker.
  3. IRS/DLC (user and basic handset data) and CPC (IMEI and feature names) consume Kafka and upsert golden_gate for the inventory report. CCS writes unbilled data and messaging usage into att_unbilled_usage.
  4. SQL Agent pushes the caches outward. For example, HYFE labels flow cache_hyfe_feed → t_field_language, which is why a UDL label change shows up in the portal.

BEST billed-data load

  1. AT&T drops BEST billed-data feeds. AFH decrypts and unzips them into Load\ToConvert\att. FileServices checks at 01:00 and emails ops if files are missing.
  2. SSIS att_integrations runs the BEST integration and the HYFE cache pull.
  3. Load jobs ("Find Extract Files", "Extract Next File") stage the data in the load DBs.
  4. "Export Next Autoload Acct" loads accounts and bills into att_config_prod_db. LENMMAProcessor then ships load logs to AT&T's Azure Log Analytics through MMA.

4. Database architecture & ER models

This section first shows which databases exist and why, then walks through the data model one area at a time. Every table, column and join in the diagrams was checked against the code in g3-core (ba-sql/src/Core/*/References/Tables, which holds the live schema, plus its stored procedures and GAS) and att-cp (Dev/SQL, Dev/Other/GoldenGate, Dev/GAS). Anything that could not be confirmed is drawn as a dotted "inferred" line.

4.1 Database architecture: core databases vs AT&T-only databases

The AT&T Wireless portal runs on eleven SQL Server databases, in two groups:

  • Shared-platform (g3-core) databases. g3-core defines five database types: config, load, usage, payment and system. Every Globys client gets its own copy of each, so these are AT&T's copies. Their tables and stored procedures come from g3-core, and att-cp may only add to them (prefixed sp_att_* procs, one table, triggers). att-cp's own README forbids overriding a core procedure with a same-named copy, after that caused two regressions (ATT-6376, ATT-6482). AT&T runs more than one copy of some types: three load databases (billed, unbilled, unbilled 2) and two usage databases (billed, unbilled).
  • AT&T Wireless-only databases. These have no g3-core equivalent. att_custom_db holds features only AT&T has. golden_gate is the landing zone for AT&T's Telegence and Premier data and for AT&T feed services. att_integrations and att_unbilled_usage belong to the AT&T SSIS pipelines.

Good to know

  • Cross-database joins are hard-coded names. att_custom_db code uses [att_config_prod_db].[dbo].t_acct or att_config_prod_db..t_acct. No synonyms or name tokens are used, so a query copied from a proc works as-is.
  • Where each database lives. Per the Confluence page "Key Tables for Golden Gate" (March 2025), golden_gate is on S3-GGDB-101, att_custom_db is on s3-db-101, and cache copies go to att_integrations and att_unbilled_usage on both S3-GGDB-101 and S3-ETL-101. Server placement is set per environment and is not in the code.
  • GoldenGate targets. The replicat files write to ODBC sources named ban and uav. Which databases those sources point at is set on the server, not in the repo.
  • Most times are Pacific. Older DATETIME columns are local Pacific time. Newer ones (characteristic tables, the ASLA event log, golden_gate last_updated_date) are UTC.

4.2 How to read the ER diagrams

Each box is one table. The header shows the table name and its database, and each row is a column. Only the columns that matter for joins and support are shown. Lines join the exact columns involved, with a bar at the "one" end and a crow's foot at the "many" end. Header colour shows who owns the table.

4.4 Identity, organizations and account access g3-core

Who is allowed to see which accounts. A client (AT&T is client_id 289) owns organizations, and organizations own accounts. Each account is placed on a node in one or more hierarchy trees. Each user gets at most one home node.

How to read it
  • Default (hierarchy) access: t_hierarchy_user gives the user a home node. t_hierarchy_query_cache expands that node to every node beneath it, and t_hierarchy_acct lists the accounts on those nodes.
  • Whitelist access: this applies only when t_client.user_acct_flg = 1 and the user has t_user_acct rows. The explicit list must still sit inside the user's organization.
  • All of this logic lives in dbo.fn_user_acct_get (with fn_user_acct_flag). It also drops accounts with display_flg = 0 unless a per-user override applies.
  • t_user has no organization_id. A user's organization comes from t_hierarchy_user.
  • link_acct_id is a generic account link that sp_acct_link_resolve uses to carry organization moves along a chain. It is not a FAN → BAN parent.
How att-cp uses g3-core here

sp_att_user_account_access_realtime_csv_set rewrites t_user_acct and clears organization_admin. sp_att_account_organization_get resolves an account's organization through the link account. The installment-plan validator repeats the whitelist check. The trigger tr_att_user_insert seeds default t_acct_query tags for new customer users.

Support tip

"User can't see an account": check the account's organization_id, then whether its t_hierarchy_acct node sits under the user's home node in t_hierarchy_query_cache. Then check whether whitelist mode applies (user_acct_flg plus t_user_acct rows). The safest test is SELECT * FROM dbo.fn_user_acct_get(...).

Changed from the previous version: t_user → t_hierarchy_user is 0..1, not 1:1. Added t_hierarchy, t_hierarchy_node, t_hierarchy_query_cache and t_user.acct_id. Accounts and users hang off hierarchy nodes, not directly off the organization. link_acct_id is 1:N.

4.5 Bills, statements and report data g3-core

How to read it

4.6 Load lineage: how a file becomes a bill g3-corenew

New in this version. Every billed row can be traced back to the exact file and record that produced it. The load database (att_load_db for billed BEST data, att_unbilled_load_db for unbilled data) records each batch and file, and the IDs are copied onto the rows that reach the portal.

How att-cp uses g3-core here

4.7 Payments g3-core

Every payment made in the portal is a t_payment row in the config database, owned by an account and a user and optionally tied to one bill. For AT&T the money itself moves at AT&T CSI. These rows are Globys's record of it.

How to read it
  • processing_result: 0 in progress, 1 successful (the only value that counts toward balance), 2 failed or rejected, 5 cancelled.
  • Online payments are grouped in a t_cart. The gateway request and response log rows in t_application_log share that id as log_correlator_id.
  • t_payment_response_code maps external response codes to a processing_result for t_external_payment imports. t_payment itself has no response-code column.
  • payment_id is issued by payment_db.t_payment_id (next diagram).
How att-cp uses g3-core here

For installment plans, item_correlator_id holds the plan's inst_seq_no. sp_att_installment_plans_list hides any plan with a successful payment. The core AttInstallmentPlansValidator calls sp_att_validate_installment_plans_for_payment before charging.

Support tip

"Payment stuck or failed": read processing_result and processing_result_msg, then find the gateway exchange in t_application_log where log_correlator_id = t_payment.cart_id.

Changed from the previous version: t_payment has no link to t_payment_response_code; that table maps codes for t_external_payment. Added t_cart. The installment link is a cross-database number match on inst_seq_no.

4.8 Saved payment methods, autopay and payment_db g3-corenew

New in this version. A saved card or bank account is a t_user_payment_info row in the config database. Its sensitive detail lives next door in payment_db. An account is on autopay when t_acct_payment_info has a row for it with a non-null autopay_enabled.

How to read it

How att-cp uses g3-core here

GAS AttPaymentTokenizer stores methods through sp_payment_info_add. AttPaymentProvider logs batch status into t_autopay_processing_log. Remittance is configured for client 289 (E:\remittance\att). t_autopay_client_setup and t_autopay_process_date show no AT&T use.

Support tip

"Autopay status wrong": check t_acct_payment_info for the acct_id. Look at autopay_enabled, and whether user_payment_info_id is -1 (external) or a real saved method. Then look in t_application_log for AutopayProvider calls that did not return 200.

4.9 Report columns and their labels core + att-cp

Report tables have generic numbered columns. t_field says what each column means for one report type, and t_field_language says what to call it on screen. A label can be overridden per language, per account and per user.

How to read it

4.10 Custom settings (t_custom_value) and how they are scoped g3-corenew

Most portal behaviour switches, such as "custom type 297" in the ASP code, are rows here. A setting (t_custom_type) has one or more values (t_custom_value), and each value is attached to the level it applies to.

How to read it
  • sp_custom_value_get looks for a value in this order: organization → account → group (through the organization, then the account) → product → client → the type's default (default_value = 1). The first match wins. The numbers in the right-hand boxes show that order.
  • There is no user-level table. A user affects the result only through their product and the account passed in.
  • CV13.CUser.GetCustomNumericValue(userId, typeId) resolves through sp_get_single_customization, which finds the user's account and then calls sp_custom_value_get.
How att-cp uses g3-core here

att-cp seeds and changes AT&T settings through its upgrade scripts, for example the "Back to Dashboard" host allowlist (custom type 10006) and email suppression. The AT&T ASP overlays read them through GetCustomNumericValue and GetCustomStringValue.

Support tip

"A setting doesn't seem to apply": check each level in resolution order for that custom_type_id. A value at organization level beats one at client level, even if the client value is newer.

Changed from the previous version: The previous version showed placeholder "scoping tables". They are now the real five tables, with the resolution order.

4.13 att-cp Area A: user and CSR event logging (security audit feed) att-cp

AT&T security-audit events are queued in att_custom_db and published to AT&T's security log audit (ASLA). Customer events come from triggers and the logout page; CSR and CAT logins are copied from core's CSR log.

How to read it
  • Event types 1–9: 1 User creation, 2 Login, 3 Logout, 4 Email update, 5 CAT Login, 6 CAT Logout, 7 CSR Account Login, 8 CSR User Login, 9 Premier CSR Login.
  • A row is either a customer event (user_id set) or a CSR event (ce_csr_user_id and ce_csr_log_id set), never both.

How att-cp uses g3-core here

4.14 att-cp Area B: device installment plans att-cp

AT&T device installment plans ("Easier Device Payoff") shown on the bills page. Only plans in billing are kept, and plans already paid through the portal are hidden.

How to read it
  • inst_info_upsert MERGEs stage_inst_info into inst_info on all four key columns (casting the numeric BAN to text). IN_BILLING rows are inserted or updated. Any other status deletes the row. The stage table is then truncated.
  • The same run syncs t_acct_permission: 20032 (installment feature) is granted to accounts with plans and removed from accounts without. 20033 (history tab) is granted once and never removed.
  • cache_refresh_state has no join. It is a single watermark row keyed by name, and no att-cp code updates it.
  • Upstream, GoldenGate replicates Telegence INST_INFO. How it reaches stage_inst_info is not in the repos.
How att-cp uses g3-core here

GAS plugin AttInstallmentPlansPlugin calls att_custom_db..sp_att_installment_plans_list. Core's AttInstallmentPlansValidator calls sp_att_validate_installment_plans_for_payment. Both read core t_acct, t_subacct, t_payment and the hierarchy tables across databases.

Support tip

"Plan still shows after payment": look for t_payment with item_correlator_id = inst_seq_no and processing_result = 1. "Feature disappeared": the account's inst_info rows were probably deleted by a non-IN_BILLING stage row, which also removes permission 20032.

Changed from the previous version: Removed the false inst_info → cache_refresh_state relationship. The stage link is a 1:1 key MERGE that also deletes. Added t_subacct, t_payment and the t_acct_permission side effect. The join to t_acct is on num only (client_id is ignored).

4.15 att-cp Area C: HYFE feed and custom report labels (UDL) att-cp

HYFE sends up to four "user-defined label" names (UDL) per FAN. They become the customer's own column headers on reports, for every BAN that belongs to that FAN.

How to read it
  • A BAN belongs to a FAN through t_acct.acct_type, which holds the FAN id. It does not use t_acct.num.
  • udl_report_field_mapping is a column mapping: UDL slot 1 means column udl_1, and so on. Each slot maps to a t_field (varchar_47–50, or nvarchar_47–50 for type 55).
  • cache_hyfe_feed_upsert MERGEs stage into cache, deletes stale labels, then MERGEs t_field_language with (field_id, language_id = 0, acct_id = BAN). user_id defaults to 0.
How att-cp uses g3-core here

att-cp installs two triggers on core t_acct. tr_att_acct_insert_hyfe_udl (after insert, BAN rows) adds the labels for a new account. tr_att_acct_update_hyfe_udl (after an acct_type change) deletes and rebuilds them. A second, older cache_hyfe_feed also exists in golden_gate (Area I). Compare the updated_date values before trusting either.

Support tip

"Default headers instead of the customer's labels": check that the BAN's t_acct.acct_type equals a cache_hyfe_feed.fan_id, that udl_N is not NULL, and that t_field_language has language_id = 0 rows for that acct_id.

Changed from the previous version: The FAN match is on acct_type, not num. The mapping points at t_field, not at cache rows. The trigger names are tr_att_acct_insert_hyfe_udl / tr_att_acct_update_hyfe_udl.

4.16 att-cp Area D: FAN cycle info att-cp

An external pipeline drops FAN and BAN bill-cycle rows into fan_cycle_info. Every hour a job stamps each account's FAN type, and each BAN bill's consolidated cycle date, onto core's characteristic tables.

How to read it
  • The job "att_custom_db - fan cycle info upsert" runs sp_att_fan_cycle_info_stage (copies rows where processed_date IS NULL) and then sp_att_fan_cycle_info_upsert.
  • Accounts are found with num = fan_id OR num = ban. The bill is found with billed_dt = ban_cycle_date AND stmnt_exist_flg = 1, which compares DATETIME with DATETIMEOFFSET.
  • When the cons_cycle value lands, the stage row is marked processed and fan_cycle_info.processed_date is set. sp_att_fan_cycle_info_purge deletes processed rows after 30 days and unprocessed rows after 60.
How att-cp uses g3-core here

Writes core t_acct_characteristic and t_billed_characteristic, the only core tables with enforced foreign keys. It also back-fills fan_type for accounts created in the last day in groups 10, 11 and 12 (Fulfillment, Billing, Reporting).

Support tip

"Rows stay unprocessed": check for a t_billed row for the BAN whose billed_dt exactly equals ban_cycle_date, with stmnt_exist_flg = 1. The bill may not have loaded yet, or a time-of-day or offset mismatch may be blocking the match.

Changed from the previous version: The stage direction was reversed: fan_cycle_info is the source, and stage is a per-run copy linked 1:1 by fan_cycle_info_id. The characteristic writes go through t_acct and t_billed, not directly.

4.17 att-cp Area E: large-account PDF queue att-cp

BANs with many lines get their large bill PDFs pre-built. After each statement load, qualifying accounts are queued here, and an external Windows service claims each row, builds the PDF and marks it done or failed.

How to read it
  • The writer is load plugin 5003, sp_large_account_pdf_details_load, which runs in the load database and writes here through t_destination_database.
  • An account qualifies when all of these hold: source_name = 'BAN', display_acct_num is not NULL, it has a bill in this batch, its organization has a customer (type-2) user, it has at least ctnCount sub-accounts, and t_bill_doc_request_log has a request for it within lookBackMonths.
  • The settings GlobysSqlPluginConfig:ctnCount, :ReportClassId and :lookBackMonths live in t_application_config.
  • Queue states: process_start_timestamp NULL means waiting; start set and end NULL means running or stuck; end set means complete; error_desc set means failed.
How att-cp uses g3-core here

The processors are sp_large_account_pdf_process_record (claims a row with READPAST), sp_large_account_pdf_complete_update and sp_large_account_pdf_error_update. Known bug: complete_update assigns @pdf_available = 1 to a variable, so pdf_available is never set to 1. Use the timestamps instead.

Support tip

"Large-account PDF never queued": check the three t_application_config values, that the account's organization has a type-2 user, and that t_bill_doc_request_log.acct_id_list is exactly that acct_id within the look-back window.

Changed from the previous version: Added the selection rules and tables. Documented that pdf_available is never set by code.

4.18 att-cp Area F: Premier user permissions (GoldenGate copy) att-cp

A GoldenGate copy of Premier's own permission tables. When a Premier user signs in, the portal reads their role and access rights here and writes the result into the portal's own t_user_permission.

How to read it
  • The reader is not in att-cp. It is g3-core GAS clients/ATT/UserProvisioningExtensions/AccessRights (Queries.cs, AccessPermissions.cs), which does ChangeDatabase("att_custom_db").

"Premier user has the wrong permissions": check that their STUB ID is in dps_user.login, that pep_profile.registration_fan or ban_id is filled, and that gg_cdr_time isn't NULL or in the future (those rows are filtered out). Also check that the permCust replicat is running.

4.19 att-cp Area G: unbilled report data (RD26, RD27, RD28) att-cp

4.21 att-cp Area I: golden_gate feed caches and data marts att-cp

The working area around the Telegence mirror. Feed services and SSIS packages keep cache_* tables up to date, procedures combine them (inventory report, org and L3 updates, MyATT filtering), and the data-mart jobs copy the caches on to other databases.

How to read it
