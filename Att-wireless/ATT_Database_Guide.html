AT&T Backend Architecture & Database Guide

How the AT&T Wireless portal backend is put together, and how its databases are laid out: the shared g3-core platform plus the AT&T-specific att-cp overlay.

The portal does two kinds of work. Live work happens while a user waits: sign-in, viewing a bill, making a payment, switching to paperless. Background work runs all the time: AT&T feeds (HYFE, Telegence and Premier via GoldenGate, BEST billed files, and unbilled usage through att_unbilled_usage) keep local copies of AT&T data fresh. Both land in SQL Server databases of two kinds. Eight are AT&T's copies of the five g3-core database types (config, load, usage, payment, system). The other four have no g3-core equivalent: att_custom_db, golden_gate, att_integrations and att_unbilled_usage.

2. Backend architecture

Start with the big picture. The backend does two kinds of work. Some happens live, while a user waits for a page. The rest happens in the background, keeping local copies of AT&T data up to date. The detailed diagram further down fills in the individual services.

2a. The big picture

What's happening, step by step

  1. A user opens the portal. An AT&T business customer (Premier or FirstNet) or an AT&T CSR opens the Bill Analyst portal, either directly or from a link in the AT&T business dashboard. Before anything else, the front door sends them to AT&T to sign in. We never see AT&T passwords; AT&T tells us who the user is.
  2. The page asks for data. Every screen (bill summary, invoices, usage, payments) is a page that asks the business logic layer for what it needs. Older screens use the classic page engine (COM / CV13, the older Windows components behind the ASP pages) and newer React screens use the GAS APIs, but both do the same job.
  3. Some answers need AT&T right now. A few things can't come from a copy because they must be live: taking a payment (AT&T CSI), fetching a bill PDF or switching paperless (Telegence, through the TLGEJB bridge), sign-in and user profiles (AT&T identity, Premier / PAM), and sending emails (CBUS). If AT&T is slow or down, the user sees it straight away.
  4. Everything else comes from our databases. Most of what a user sees (accounts, bills, reports, users, permissions, labels) is read from Globys's own SQL Server databases, which is why most screens are fast. Changes the user makes are saved there too.
  5. AT&T keeps sending us data. In the background, independent of any user, AT&T streams changes to us: Kafka events, message queues, a live copy of the Telegence database (accounts and unbilled usage, through GoldenGate), and file drops. The files are BEST for billed data, plus unbilled usage files from Telegence and Enabler.
  6. Background workers keep the copies fresh. Small Globys services read those feeds and write them into the databases. SQL Agent jobs then move the data into the tables the portal reads, so by the time a user opens a page the data is already local.

The rule of thumb for support: an error or timeout on a page usually means the live path (steps 1–4): the portal, GAS, or an AT&T system it calls. Old, missing or wrong data with no error usually means the background path (steps 5–6): a feed or worker has stopped, or a sync job hasn't run yet.

What's happening in each area

Each card matches a lettered area of the diagram and uses the same box names, in the same order. The grey text after a name is the real system name, which matches the small grey text in the diagram.

AWhere users come from

  • AT&T customers & support agents: AT&T business users (Premier, FirstNet) and AT&T CSRs open the portal in a browser. They go straight to the customer portal.
  • AT&T business dashboard Convergence BDC Dashboard · business.att.com/manage: a dashboard for AT&T business customers, which links them into our portal without a second login. There are two kinds of link:
    • Page links (statements, one statement, payment, paperless, autopay) go straight to the customer portal through a bridge page. The dashboard and portal share the same sign-in, so the user is already signed in. Paperless and autopay can even be shown inside the dashboard.
    • Report downloads go through the link router, which checks a signed pass from the dashboard.
    When a user arrives from the dashboard, the portal shows a "Back to Dashboard" link.

Nothing runs here. This is just where traffic starts.

BFront door

  • Link router Redirector: checks that a dashboard link is genuine, then forwards the user to the right page in the portal.
  • Customer portal (web pages) Bill Analyst: the screens users see. Older classic screens get their data from the classic page engine, and newer screens get theirs from the main API. It carries AT&T and FirstNet branding plus a few AT&T-only pages (logout, bill PDF, remittance PDF).
  • Sign-in service GAS AuthSite: when a user needs to sign in, it sends them to AT&T sign-in to check the login. It then asks the main API to set up the user's session.

When it breaks: users can't reach the portal, get stuck in a login loop, or a dashboard link lands on the wrong page.

CBusiness logic

  • Classic page engine COM / CV13: the older code behind classic screens. For each action it runs one saved database query and returns the result. It covers bills, account hierarchy, reports and payments. When a user opens a bill it asks the bill document service to get the bill PDF.
  • Main API (business services) GAS Services: the modern engine behind newer screens: payments, user setup, reports, organisations, invoices and disputes. It includes AT&T add-ons for installment plans and data pooling. It takes payments through AT&T payments, looks up users in AT&T user profiles, and asks the billing bridge for bills.
  • Bill document service GCS + BDF: creates and serves bill PDFs. PDF orders wait in a queue that is checked every minute, and finished files go to PDF & file handling.
  • Usage bridge EnablerEJB and Billing bridge TLGEJB: translators. AT&T's billing and usage systems only accept a special kind of Java call, so these two services turn our normal requests into those calls. The billing bridge reads bills and changes paperless settings in the AT&T billing system. The usage bridge can read usage details from the AT&T usage system, but nothing in att-cp calls it, and Enabler isn't in the runbook's list of AT&T APIs. Enabler usage reaches us as files instead, so the usage bridge is probably unused.
  • Paperless sync PBS service: when a customer turns paperless billing on or off, it passes the change to the billing bridge.
  • Email sender Notification service: builds emails and sends them through the AT&T email service.
  • The thick line on the left shows that the classic page engine and the main API both read and write the databases.

When it breaks: one feature fails with an error. For example, a payment fails, a bill PDF won't open, a paperless change doesn't stick, or an email never arrives.

DBackground workers

These run all the time, whether or not anyone is using the portal. Each one takes something AT&T sends (the blue boxes at the top of this area) and saves it into a database.

  • PDF & file handling PDF Cataloger · Large-BAN PDF: takes the PDF files from the bill document service, records each one in the main portal databases, and moves files to where they belong. It also handles PDFs for very large accounts.
  • File loader SSIS pipelines: when AT&T's file drops arrive, it loads them. The files go to different places:
    • BEST: AT&T's billed data (bills and statements). It goes into the loading area and then the main portal databases.
    • Unbilled usage files: Enabler (unbilled usage summary and detail) and Telegence (unbilled usage). Pipelines enabler, enabler_unbilled_detail, telegence_unbilled and mms load them into AT&T data copies.
    • CARE: the device inventory feed, one of the inventory report's inputs (batch type "Care", ATT-2837).
  • Billing DB mirror Oracle GoldenGate: every change in the AT&T billing system (Telegence) database is copied into AT&T data copies. It carries billing account and reference data (customers, billing accounts, subscribers, addresses, devices, service agreements and features), payment transactions, installment plans (INST_INFO), bill cycle control, and unbilled usage (the usage and pnbi* copies). SQL Agent jobs then turn this into payments, autopay status, paperless status and inventory report data. It does not carry billed statements; those come from BEST.
  • Account & label feeds HYFE · Platform Handler: read AT&T's Solace message queues and save them into AT&T data copies. HYFE carries foundation accounts (FANs) and organisations, including custom field labels (UDL). Platform Handler carries which bill presentation system (handler) each foundation and billing account uses.
  • Event readers CCS · IRS · CPC · ASLA: read AT&T's Kafka event streams. CCS carries unbilled data and messaging usage detail, saved into unbilled usage. IRS/DLC (user and basic handset data) and CPC (handset IMEI and feature names) feed the device inventory report in AT&T data copies. ASLA works the other way: it sends our user and CSR login/logout events to AT&T's security log audit, which is why that arrow points both ways.

When it breaks: there's no error, but data goes stale or missing. For example, yesterday's bill isn't there, a new label doesn't show, the device list is old, or unbilled usage stops changing.

EDatabases

  • Main portal databases att_config_prod_db · att_custom_db · cv_system_db: what the portal reads. They hold accounts, users, bills, permissions, AT&T-only tables, the bill document list and emails.
  • Loading area att_integrations · att_load_db: BEST billed files are unpacked and checked here first, then loaded in to the main portal databases.
  • AT&T data copies golden_gate: Telegence account data and unbilled usage (from the billing DB mirror), unbilled usage files from Telegence and Enabler, and everything the feed readers save. Scheduled database jobs copy it on to the loading area and to unbilled usage, and to the main portal databases (not drawn).
  • Unbilled usage att_unbilled_usage: usage that isn't on a bill yet. It's copied on from AT&T data copies, plus 5G usage saved directly by the event readers.

When it breaks: everything slows down or fails at once. If only some data is wrong, the cause is usually a background worker (area D) or a copy job, not the database itself.

FAT&T systems

These are owned and run by AT&T, not Globys. Top to bottom, as in the diagram:

  • AT&T sign-in: confirms who the user is (Premier / FirstNet login).
  • AT&T payments + T&C consent CSI · SmartPay · ExpressPay: CSI (7 calls) takes one-time payments (bills and installment-plan payoff) and manages autopay enrolment. SmartPay (2 calls) handles payment terms and conditions. ExpressPay is AT&T's payment page, embedded in ours, where users add a card or bank account. Autopay payments themselves are processed by AT&T outside our application.
  • AT&T user profiles & permissions Premier profile · PAM: who the user is and which accounts they can see.
  • AT&T email service CBUS: delivers emails for us.
  • AT&T billing system Telegence: sends us account data and unbilled usage in the background, and serves bill images (PDFs) and paperless settings live through the billing bridge.
  • AT&T usage system Enabler: unbilled usage (summary and detail), sent to us as files.
  • AT&T upgrade eligibility MRE API: device upgrade eligibility for the inventory report. It isn't drawn. The inventory report pipeline calls it through the "MRE Updater" jobs.

When it breaks: we can't fix it ourselves. Confirm our side is healthy (the service's health check and logs), then raise it with AT&T through the escalation path in this customer's runbook.

GGlobys cloud

  • Globys cloud data platform Forge · Azure: Globys's newer platform. It is becoming the main home for bills, usage (call records) and payments. It connects to the portal in four ways:
    • It receives a copy of every change in the main portal databases (accounts, users, payments, disputes, permissions and more), using SQL Server change capture. This is the long arrow along the bottom.
    • Usage data is exported to it as files. After export, the usage rows can be deleted from our SQL databases.
    • It runs the back end of the AT&T business dashboard, including the signing keys the link router checks.
    • It sets up users by calling our main API (not drawn).

Watch out: it doesn't copy anything back to our databases. If data is missing from SQL but the customer can see it, it may now live only in the cloud platform, or it was exported and deleted from SQL.

Billed vs unbilled: where each comes from

A common source of confusion. Billed means the usage and charges on a bill that has already been produced. Unbilled means usage in the current, still-open bill cycle.

3. Key flows

The same diagram, traced for the requests and jobs that most tickets involve.

Sign-in

  1. The user arrives from Premier / FirstNet, or from the AT&T business dashboard. Dashboard page links reuse the shared sign-in. Report-download links go to /redirector, which checks the signed token against keys held on the Globys cloud data platform (Forge).
  2. GAS AuthSite completes SAML, OAuth/OIDC or CAS cookie exchange with AT&T identity.
  3. UserProvisioning calls the Premier profile service (HALO client certificate) or PAM. It then writes the user, accounts and permissions into att_config_prod_db.
  4. The browser lands on the Bill Analyst portal. Login and logout events go to att_custom_db, and the ASLA publisher sends them on to AT&T Kafka.

Viewing a bill

  1. The ASP statement page calls the classic page engine (COM), which looks up the document endpoint in t_bill_doc_type_config.
  2. The classic page engine calls the BDF Globys.Att.Documents WCF service, which runs inside GCS.
  3. Bill lists and bill images for Telegence accounts come through TLGEJB (/statement/pdf) into Telegence EJBs.
  4. Report and PDF orders are queued in ROQS. BdfOrderProcessor (every minute) writes them to the ROP share and the PDF pickup folder, and PDF Cataloger catalogs them into cv_system_db.

Making a payment / autopay

  1. The React payment UI calls GAS Payments (ServiceMcp).
  2. Card and bank details are captured in AT&T's ExpressPay page, embedded in ours, and tokenized (/payments/v1/tokenize/init/attcc | atteft).
  3. The ATT_Common CsiApiService calls AT&T CSI over SOAP: AddPayment, ManageAutomaticPayments, InquirePayments and so on.
  4. SmartPay T&C consent is recorded through the corpops TermsAndAgreement API. Payment state is in the payment DBs and golden_gate autopay caches.

Paperless billing

  1. The paperless / bill-format change is made in the portal and saved in att_config_prod_db.
  2. The PBS service calls TLGEJB /bill/addressInfo/{acct} (GET / PUT / DELETE).
  3. TLGEJB updates the bill format in Telegence over t3 EJB.
  4. The golden_gate job "Run GG Paperless Billing Integration" keeps the paperless_bill_state cache in step.

Real-time feeds (continuous)

  1. GoldenGate replicates Telegence Oracle schemas (BAN, reference data, unbilled usage) into golden_gate.
  2. HYFE reads FAN/UDL, PDP and authorized-email-domain messages from the AT&T broker. Platform Handler reads platform events from the same broker.
  3. IRS/DLC (user and basic handset data) and CPC (IMEI and feature names) consume Kafka and upsert golden_gate for the inventory report. CCS writes unbilled data and messaging usage into att_unbilled_usage.
  4. SQL Agent pushes the caches outward. For example, HYFE labels flow cache_hyfe_feed → t_field_language, which is why a UDL label change shows up in the portal.

BEST billed-data load

  1. AT&T drops BEST billed-data feeds. AFH decrypts and unzips them into Load\ToConvert\att. FileServices checks at 01:00 and emails ops if files are missing.
  2. SSIS att_integrations runs the BEST integration and the HYFE cache pull.
  3. Load jobs ("Find Extract Files", "Extract Next File") stage the data in the load DBs.
  4. "Export Next Autoload Acct" loads accounts and bills into att_config_prod_db. LENMMAProcessor then ships load logs to AT&T's Azure Log Analytics through MMA.

4. Database architecture & ER models

This section first shows which databases exist and why, then walks through the data model one area at a time. Every table, column and join in the diagrams was checked against the code in g3-core (ba-sql/src/Core/*/References/Tables, which holds the live schema, plus its stored procedures and GAS) and att-cp (Dev/SQL, Dev/Other/GoldenGate, Dev/GAS). Only joins confirmed in code are drawn.

4.1 Database architecture: core databases vs AT&T-only databases

The AT&T Wireless portal runs on twelve SQL Server databases. In production they sit on three database servers: S3-DB-101 (the portal databases and att_custom_db), S3-GGDB-101 (live copies of golden_gate and att_unbilled_usage, fed by GoldenGate on S3-GG-101) and S3-ETL-101 (att_integrations). By origin they fall into two groups:

  • Shared-platform (g3-core) databases. g3-core defines five database types: config, load, usage, payment and system. Every Globys client gets its own copy of each, so these are AT&T's copies. Their tables and stored procedures come from g3-core, and att-cp may only add to them (mostly sp_att_* procs plus the large-account PDF procs, a few tables such as t_large_account_pdf_details and t_field_label_load_configuration, and triggers). att-cp's own README forbids overriding a core procedure with a same-named copy, after that caused two regressions (ATT-6376, ATT-6482). AT&T runs more than one copy of some types: three load databases and two usage databases. att_load_db loads billed data. att_unbilled_load_db loads all unbilled summary and detail data, which comes through att_unbilled_usage. att_unbilled_load_db_2 loads all inventory report data, which comes through golden_gate. Both unbilled load databases load into the same usage database, att_unbilled_usage_db; billed data goes to att_usage_prod_db.
  • AT&T Wireless-only databases. These have no g3-core equivalent. att_custom_db holds features only AT&T has. golden_gate is the landing zone for AT&T's Telegence and Premier data and for AT&T feed services. att_integrations and att_unbilled_usage belong to the AT&T SSIS pipelines.

4.2 How to read the ER diagrams

Each box is one table. The header shows the table name and its database, and each row is a column. Only the columns that matter for joins and support are shown. Walking through the model

Who owns what

A bridge table with user_id, acct_id and a version row stamp. One row means "this user may see this account", and a unique index on (user_id, acct_id) prevents duplicates. It links t_user and t_acct only by matching IDs; there's no foreign key, so orphan rows are possible.

A common mix-up

4.6 Load lineage: how a file becomes a bill g3-core

Every billed row can be traced back to the exact file and record that produced it. The load database (att_load_db for billed BEST data, att_unbilled_load_db for unbilled summary and detail data, att_unbilled_load_db_2 for inventory report data) records each batch and file, and the IDs are copied onto the rows that reach the portal.

Walking through the model

This diagram shows how an AT&T bill file becomes a bill in the portal, and how to trace any bill row back to the file it came from. The load database (att_load_db) is the workshop where files are read and cleaned; the portal database (att_config_prod_db, plus att_usage_prod_db) is where finished bills live.

AT&T file arrives
  → t_batch            a delivery (one bill run)
  → t_extract_file     one file in that delivery
  → t_<type>_extract   its records, as read from the file (raw text)
  → t_<type>_load      the same records, cleaned, with Globys IDs looked up
  → t_billed / t_statement / t_report_data_NN   the finished bill
The load-side tables
  • t_batch is one delivery, with its file name and created / ready / completed times. No completed_datetime means it hasn't finished.
  • t_extract_file is one file: its extract_file_id (the key for tracing), file_type_id (what kind of file, see t_file_type), record_count and Error_code. It matches t_batch by file name, not by ID.
  • t_<type>_extract / _load is a pair of staging tables for each kind of data (for example t_statement_extract and t_statement_load). Extract holds AT&T's account numbers and values as text; load holds proper types plus the Globys acct_id and billed_id. Each record keeps extract_file_id + extract_id (its record number).
  • t_load_status tracks a file's progress (IDLE = not loading). t_exceptions lists records that failed cleaning, pointing at the exact extract_file_id + extract_id.
  • t_acct_billed_batch records which accounts and bills each batch loaded.
How the trace works

When records reach the portal, the load stamps its IDs on them: t_billed and t_billed_subacct carry batch_id, and every t_statement and t_report_data_NN row carries extract_file_id + extract_id. So any bill line leads back to the exact record in the exact file. After export, sp_acct_export deletes the statement _load rows, so an empty t_statement_load is normal.

HYFE sends up to four "user-defined label" names (UDL) per FAN. They become the customer's own column headers on reports, for every account whose t_acct.acct_type holds that FAN (in practice, its BANs).

Walking through the model

This diagram answers where a customer's own report column headers come from. HYFE is the AT&T feed of foundation accounts (FANs, the parent account that groups BANs). For each FAN it can send up to four UDLs (user-defined labels). att-cp turns them into column names on that customer's reports.

stage_hyfe_feed → cache_hyfe_feed        one row per FAN, udl_1 … udl_4
  + t_acct (acct_type = fan_id)          the BANs under that FAN
  + udl_report_field_mapping → t_field   which report column each UDL renames
  → t_field_language                     the label, stored per BAN
The tables
  • stage_hyfe_feed is the incoming HYFE rows. It is merged into the cache and then emptied.
  • cache_hyfe_feed is the latest copy, one row per fan_id. udl_1 to udl_4 hold the label text.
  • t_acct is core's account. A BAN belongs to a FAN when acct_type equals the fan_id.
  • udl_report_field_mapping says, per report type, which column each UDL slot relabels (udl, report_type_id, field_id).
  • t_field is a report column (for example varchar_47). t_field_language holds its display name. A row with language_id = 0 and a BAN's acct_id overrides the name for that account only.
How labels stay current

cache_hyfe_feed_upsert rewrites the labels after each feed and deletes ones HYFE no longer sends. Two triggers on t_acct add labels for a new BAN, and rebuild them when its acct_type changes.

4.16 att-cp Area D: FAN cycle info att-cp

An external pipeline drops FAN and BAN bill-cycle rows into fan_cycle_info. Every hour a job stamps each account's FAN type, and each BAN bill's consolidated cycle date, onto core's characteristic tables.

Walking through the model

This diagram answers how each account gets its FAN type, and each bill its consolidated cycle date. A FAN is the parent account that groups BANs (billing accounts). An outside pipeline sends rows that pair a FAN with one of its BANs, with both cycle dates. An hourly job copies that onto core's accounts and bills.

fan_cycle_info            rows from the pipeline (processed_date NULL = to do)
  → stage_fan_cycle_info  this run's copy
  → t_acct                num = fan_id OR num = ban
      → t_acct_characteristic    name 'fan_type'
      → t_billed (billed_dt = ban_cycle_date)
          → t_billed_characteristic  name 'cons_cycle' = fan_cycle_date
The tables
  • fan_cycle_info is the pipeline's table: fan_id, ban, fan_type, fan_cycle_date and ban_cycle_date. processed_date is set once the row has been applied.
  • stage_fan_cycle_info is a per-run copy of the unprocessed rows. It links back by fan_cycle_info_id, uses processed to mark success, and is emptied at the end of each run.
  • t_acct and t_billed are core's accounts and bills. Only bills with stmnt_exist_flg = 1 are used.
  • t_acct_characteristic and t_billed_characteristic are core's name/value tables for extra facts about an account or a bill. The job writes value_string and value_datetime.

4.17 att-cp Area E: large-account PDF queue att-cp

BANs with many lines get their large bill PDFs pre-built. After each statement load, qualifying accounts are queued here, and an external PDF service (not in these repos) claims each row, builds the PDF and marks it done or failed.

Walking through the model

This diagram answers which large accounts get their bill PDFs built ahead of time, and how far each one has got. A large account is a BAN (billing account) with many CTNs (phone lines, one t_subacct row each). After a statement load, qualifying bills are queued in one table, and a separate PDF service works through the queue.

The tables
  • t_acct is the account. It must have source_name = 'BAN' and a display_acct_num.
  • t_subacct gives the line count. It must reach the ctnCount setting.
  • t_billed is the bill. Its batch_id must be the load that just ran.
  • t_bill_doc_request_log records bill document requests. There must be a recent one (request_date) for this account (acct_id_list) and this document type (doc_type_id).
  • t_large_account_pdf_details is the queue: one row per account, bill and report subclass (acct_id, billed_id, report_subclass_id). document_id is the row's id.
How the queue works

The service claims a row whose process_start_timestamp is NULL and stamps the start time. On success it sets process_end_timestamp. On failure it writes error_desc and leaves the end time NULL. Read progress from these three columns, not from pdf_available.

4.18 att-cp Area F: Premier user permissions (GoldenGate copy) att-cp

A GoldenGate copy of Premier's own permission tables. When a Premier user signs in, the portal reads their role and access rights here and writes the result into the portal's own t_user_permission.

Walking through the model

This diagram answers "what is this Premier user allowed to do in the portal?" Premier is the AT&T system these users sign in through. GoldenGate (Oracle's replication tool) copies its permission tables into att_custom_db. At sign-in, g3-core GAS reads them and saves the result in the portal's own t_user_permission.

STUB ID  (t_user.login = dps_user.login)
  → dps_user_roles      the user's role (tcm, cru …)
  → rights from role + user            (tcm)
     or from FAN + BAN via pep_profile  (cru)
  → pep_function        defaults fill the gaps
  → t_user_permission   negative = 1 means denied
The tables
  • t_user is the portal user. Its login is the STUB ID, Premier's ID for the person. t_user_permission has one row per user_id + permission_id; negative = 1 means denied.
  • dps_user is the Premier user: id is Premier's key, login is the STUB ID. pep_profile shares the same id (one profile per user) and holds registration_fan and ban_id.
  • dps_user_roles gives the user's role in atg_role. That value is the role_id in pep_role_access_rights.
  • pep_role_access_rights, pep_user_access_rights, pep_fan_access_rights and pep_ban_access_rights list rights, one access_right_id per row, for a role, a user, a FAN (foundation account) or a BAN (billing account number).
  • pep_function is the list of right names (id). strict_f = 1 marks a right that is granted by default.
How the rights combine

Each access_right_id is an effect letter, a dash and a right name, for example G-Shop Premier Store (G grant, D deny, A approve). The code takes a parent list and a child list: role and user rights for tcm users, FAN and BAN rights for cru users. The child wins, and pep_function defaults fill in any right still missing.

4.19 att-cp Area G: unbilled report data (RD26, RD27, RD28) att-cp

AT&T's unbilled reports. They use the same generic fact-table shape as core's billed t_report_data_NN, but they live in att_unbilled_usage_db. Two load databases feed it: att_unbilled_load_db loads all unbilled summary and detail data (arriving through att_unbilled_usage), and att_unbilled_load_db_2 loads all inventory report data (arriving through golden_gate).

Walking through the model

This diagram answers "where do AT&T's unbilled-side reports live, and what do their columns mean?" There are three: RD26 (unbilled billing-account pooling), RD27 (Inventory) and RD28 (unbilled details). All unbilled summary and detail data comes through att_unbilled_usage into att_unbilled_load_db. All inventory report data comes through golden_gate into att_unbilled_load_db_2. Both load into the same usage database, att_unbilled_usage_db, where rows are tied to portal accounts by Globys IDs.

The tables
  • t_report_data_26 / 27 / 28 hold one row per report line. report_data_NN_id is the clustered key. acct_id, subacct_id and billed_id point at core t_acct, t_subacct and t_billed. extract_file_id + extract_id lead back to the file and record the row came from.
  • The data itself sits in generic, numbered columns: varchar_1–varchar_50, numeric_1–numeric_40, plus int_, datetime_ and similar sets.
  • t_extract_file (in each unbilled load database) is one loaded file. file_type_id 42, 43 and 44 are RD26, RD27 and RD28; in att_unbilled_load_db only 42 and 44 are enabled.
  • t_field gives the generic columns their meaning. For a report_type_id (26–28), nme is the column name (such as int_2) and display_nme is the SQL expression the report uses to show it.
  • t_report_type_client_setup lists the report types set up for a client (client_id 289 is AT&T), with their report_type_name.
How to read a column

A value in t_report_data_26.int_2 means nothing on its own. Find the t_field row with report_type_id = 26 and nme = int_2. Its display_nme is a formula that works out the days left from datetime_1 and datetime_2.

4.20 att-cp Area H: Telegence mirror tables (GoldenGate) att-cp

Near-live copies of AT&T's Telegence billing tables, kept up to date by Oracle GoldenGate. The Telegence schema uses AT&T keys (BAN, CTN, SOC) and has no Globys IDs.

Walking through the model

This diagram answers "what does AT&T's billing system say about this account, line or plan?" Telegence is AT&T's Oracle billing system. GoldenGate copies its changes into golden_gate almost live. The tables keep AT&T's own keys: BAN (billing account number), CTN (a line's phone number) and SOC (AT&T's code for a plan or feature). There are no Globys IDs; the way to a portal account is cache_account_detail (see 4.21).

BILLING_ACCOUNT (BAN)
  ├─ BILL, BILLING_PARAMETERS    bills and bill settings
  └─ SUBSCRIBER (CTN)            the lines on the account
       ├─ SERVICE_AGREEMENT → SOC   plans and features
       └─ PHYSICAL_DEVICE           SIM and handset
The tables
  • BILLING_ACCOUNT is one account: BAN (a number), FAN_ID (its foundation account), BILL_CYCLE and BAN_STATUS (O and S are shown). Only LIABILITY_TYPE = CLB accounts go into the inventory report; AUTO_GEN_PYM_TYPE is the autopay setting.
  • CYCLE_CONTROL is one bill-cycle run (CYCLE_CODE + year + month), with CYCLE_CLOSE_DATE and US_PHYSICAL_NAME, the name of that run's unbilled usage table.
  • BILL is one bill per BAN + BILL_SEQ_NO. BILLING_PARAMETERS holds bill settings per BP_BAN; BP_MEDIA_CATEGORY = PA means paperless.
  • SUBSCRIBER is one line: SUBSCRIBER_NO is the CTN, CUSTOMER_BAN its BAN, SUB_STATUS A active, S suspended, C cancelled.
  • SERVICE_AGREEMENT lists a line's SOCs. SERVICE_TYPE = P is the price plan, and a NULL EXPIRATION_DATE means still live. SOC describes each code (SOC_MED_DESC).
  • PHYSICAL_DEVICE holds the line's SIM (EQU_TYPE S) and handset IMEI (I) in UNIT_ESN.
How changes are picked up

Several mirror tables have a received_dt column. It is set when a row arrives and re-stamped by an update trigger when GoldenGate changes it. Procedures such as cache_account_detail_att_update only look at rows with a received_dt newer than their last run.

4.21 att-cp Area I: golden_gate feed caches and data marts att-cp

The working area around the Telegence mirror. Feed services and SSIS packages keep cache_* tables up to date, procedures combine them (inventory report, org and L3 updates, MyATT filtering), and the data-mart jobs copy the caches on to other databases.

Walking through the model

This diagram answers "where do the golden_gate cache tables come from, and how are they copied on?" Feed services and SSIS packages (SQL Server Integration Services, Microsoft's data-loading tool) keep the cache_* tables current. Procedures combine them with the Telegence mirror (4.20). Data-mart jobs then copy caches to other databases; a data mart is a copy kept for another system.

The tables
  • cache_account_detail is the portal's account detail, one row per acct_id (the Globys account ID). cache_account_detail_upsert updates it from stage_account_detail, adds new accounts, then empties the stage table. acct_num is the AT&T account number as text and organization_num the portal organization. att_display_flg is 1 when Telegence's BAN_STATUS is O or S.
  • cache_hyfe_feed has one row per fan_id from HYFE, AT&T's feed of foundation accounts (FANs) and organizations. agreement_id is HYFE's organization (the "L3"); udl_1 … udl_4 are custom labels.
  • hyfe_l3_agreement_changes logs each FAN where the portal organization (current_l3) differs from HYFE's (updated_l3).
  • cache_platform_handler_feed says which AT&T app handles a FAN (acct_num, handler_app_name). MyAtt FANs are left out of the inventory report.
  • cache_hyfe_pdp_package lists a FAN's data packages (fan_id + pkg_id); cache_hyfe_pdp lists the network settings in a package (apn_name, is_5g). They share pkg_id, but no code joins them.
How the data-mart copy works

data_mart_subscriptions says what to copy (an SSIS package_name). data_mart_subscribers says where (data_mart_server + data_mart_name). The procedure data_mart_cache_refresh starts each active subscriber's package with that target and logs a data_mart_executions row. It later fills in execution_status from SSISDB, the SSIS run log.

Not found in either repository, so it is not drawn: the loaders that fill stage_inst_info, stage_hyfe_feed and fan_cycle_info; the ASLA publisher and large-account PDF Windows services; the SSIS packages account_detail_cache_refresh.dtsx, premier_custom_db_migrate.dtsx and att_inventory_report_runner.dtsx; and the production values of the large-account PDF settings.
